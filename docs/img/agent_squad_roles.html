EDW → Databricks · agent architectures

Migration agents are not all built the same.

Each one exists for a different job — entry, orchestration, assessment, conversion, proof, verdict, or live observation. Once that clicks, the squad stops looking like a list of names and starts looking like different tools for different shapes of work.

Eight agent architectures

Same migration. Different wiring.

edw-start
Front door + phrase menu. Soft status only — no migration until you pick a track.
edw-demo-guide
Track A walkthrough — checkpoints, examples, and a clean handoff into the coordinator.
edw-coordinator
Owns the run_id. Discovers, lands, fans out converts, then tests and gates.
edw-assess
Readonly inventory → migration backlog. Empty backlog is still a valid outcome.
edw-convert × ≤5
Parallel fan-out. One routine in → silver/gold Spark SQL notebook out.
edw-test
Readonly proof. Bronze counts must match the live federated source.
edw-gate
Deterministic ship / no-ship from inventory, conversions, and reconcile proof.
Observe
Three live URLs: Control Plane, Genie Q&A, and MLflow span trees.

Source objects are not all migrated the same

Tables land. Views skip. Procs become Spark SQL.

LAND

Base tables

Federation → land bronze.*

1:1 landed copies with audit columns. This is the only object type that is copied into bronze.

SKIP

Source views

Visible in discovery · not landed

Seen, counted, and left behind. Migration lands base tables only — views stay at the source.

CONVERT

Procs / routines

Convert → Spark SQL notebooks

When a backlog exists, parallel convert agents rewrite logic into silver/gold notebooks and job wiring.

Type start → pick 1 / 2 / 3. Agents write disk handoffs; you watch the three observe URLs.
